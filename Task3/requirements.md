# Требования к внешним интеграциям — сервисы «Умный дом»


Архитектурное решение: внутри домена ЖКУ добавляется контейнер smart-home-service - антикоррупционный слой и точка единого контроля над интеграцией с партнёром со своей БД smart-home-db (списки доступа, журналы событий). Мобильное приложение собственников обращается к smart-home-service, а не к платформе партнёра напрямую. Это прямое следствие проблем компании: ранее партнёрские API УК работали без единых политик безопасности, и партнёры могли видеть/менять чужие данные.

Биометрические данные (лицо) и видеоряд являются специальной категорией персональных данных по ФЗ-152; обработка требует отдельного согласия и повышенных мер защиты.

---

## 1. Требования к безопасности

### 1.1. Разграничение доступа
- **R1.** Доступ собственника ограничивается его жилым комплексом и квартирой: собственник может управлять доступом только к устройствам своего ЖК и просматривать только свои события. Проверка выполняется в smart-home-service на основе данных о собственности из CRM/tenant-core-app.
- **R2.** Партнёр не может получать данные о собственниках и ЖК чужой управляющей компании. Каждый запрос к платформе партнёра содержит только идентификаторы, привязанные к конкретному ЖК; сквозной идентификатор собственника партнёру не передаётся (используются псевдонимы/токены привязки устройства).
- **R3.** Создаётся замкнутый контур умного дома: mobile app -> smart-home-service -> платформа партнёра. Прямой доступ мобильного приложения к API партнёра запрещён.
- **R4.** Менеджер УК управляет списками доступа только в рамках своего ЖК (принцип минимальных привилегий, RBAC с привязкой к ЖК).

### 1.2. Защита данных
- **R5.** **Классификация данных:** биометрия (лицо), видеоряд, ПД собственников — конфиденциальные/секретные данные согласно политике классификации (Task 1). Применяются соответствующие меры.
- **R6.** **Шифрование:** TLS 1.2+ для передачи; шифрование at-rest в smart-home-db и в хранилище партнёра; биометрические шаблоны хранятся в виде необратимых хэшей/векторов, а не исходных изображений.
- **R7.** **Минимизация данных:** партнёру передаются только данные, необходимые для распознавания (шаблон лица, номер авто, признак разрешения), без паспортных и контактных данных собственника.
- **R8.** **Согласие и ФЗ-152:** получение и хранение письменного/электронного согласия собственника на обработку биометрии; возможность отзыва согласия с удалением данных у партнёра (процедура по контракту).
- **R9.** **Журналирование:** все операции доступа (открытие двери, распознавание, изменение списков доступа) фиксируются в smart-home-db с указанием субъекта, объекта, времени и результата; журналы передаются в DWH/BI по CDC для аудита.
- **R10.** **Безопасное уничтожение:** при выводе устройства/собственника — удаление биометрических шаблонов и у партнёра, и в smart-home-db.

### 1.3. Сетевая безопасность
- **R11.** Трафик к платформе партнёра проходит через firewall/API-шлюз; разрешён только явный whitelist доменов и IP партнёра.
- **R12.** Вебхуки событий от партнёра принимаются только на выделенный эндпоинт smart-home-service за firewall, с проверкой подписи.
- **R13.** Сегментация: smart-home-service размещён в изолированном сетевом сегменте ЖКУ; доступ к smart-home-db только с smart-home-service.

### 1.4. Надёжность и инциденты
- **R14.** Команды открытия doors/шлагбаума идемпотентны; при недоступности партнёра сохраняется локальный fallback (классический видеодомофон/кнопка, списки доступа в последнем состоянии на стороне партнёра).
- **R15.** SLA партнёра по доступности и времени реакции; процедура эскалации инцидентов; уведомление ИБ PropDevelopment о подозрительной активности (аномальные попытки доступа, перебор).
- **R16.** В договоре с партнёром — обязательство по соблюдению ФЗ-152, регламент обработки ПД, право аудита, ответственность за утечку.

## 2. Протоколы аутентификации и авторизации

### 2.1. Аутентификация конечных пользователей внутри системы (собственников, менеджеров УК)
- **A1.** Через существующий auth-service-1 OAuth 2.0 Authorization Code Flow + PKCE (мы используем моб приложение).
- **A2.** Выпуск access token и refresh token.
- **A3.** MFA рекомендуется для операций изменения списков доступа и работы с биометрией.

### 2.2. Авторизация
- **A4.** RBAC + ABAC: роли (собственник, менеджер УК, администратор) + атрибуты (жилой комплекс, квартира). Claim tenant_id/building_id в токене ограничивает доступ.
- **A5.** На каждое действие — проверка владения ресурсом в smart-home-service.
- **A6.** Принцип минимальных привилегий для менеджеров УК: только свой ЖК.

### 2.3. Аутентификация между системами (service-to-service)
- **A7.** smart-home-service и платформа партнёра: взаимная TLS-аутентификация (mTLS) с клиентскими сертификатами; сертификаты с ротацией.
- **A9.** Вебхуки событий от партнёра: аутентификация по HMAC-подписи тела запроса (согласованный секрет, ротация) + проверка IP-источника; опционально mTLS.
- **A10.** smart-home-service и внутренние сервисы: внутренний токен сервисного аккаунта / mTLS.

## 3. Организация взаимодействия между системами предприятия и внешней платформой

- **I1.** Единственная точка интеграции с партнёром - контейнер smart-home-service. Никакая другая система PropDevelopment не обращается к API партнёра напрямую.
- 

- **I2.** API-контракт с партнёром фиксируется в OpenAPI-спецификации, хранится в репозитории PropDevelopment; версионирование обязательно.
- **I3.** Перед внедрением контракт проходит проверку ИБ на категории передаваемых данных (не должно быть избыточных ПД) и на отсутствие возможностей доступа к чужим ЖК (см. проблему партнёрских API УК из описания).
- **I4.** Совместимая обратная совместимость: изменения только с увеличением версии; деградация по согласованию.

- **I5.** Весь трафик к партнёру должен идти через API-шлюз с rate-limiting, валидацией запросов, логированием.
- **I6.** Параметризация по ЖК: каждый запрос несёт идентификатор жилого комплекса; партнёр обязан изолировать данные по этому идентификатору.
- **I7.** Мониторинг и метрики: задержки, ошибки, объём событий; алерты в SIEM/систему мониторинга при аномалиях.

- **I8.** События от партнёра сохраняются в smart-home-db.
- **I9.** Сроки хранения событий и биометрии определяются политикой хранения и ФЗ-152; автоматическое удаление по истечении срока.

- **I10.** Договор с партнёром: регламент обработки ПД, ответственность, право аудита, уведомление об инцидентах в течение согласованного срока (например, 24 часа).
- **I11.** Все изменения интеграции согласовываются со специалистом ИБ
